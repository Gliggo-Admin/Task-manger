Firebase Security Rules for Attendance System

Learn how to properly secure your Firebase Firestore database for your attendance management system

Current Rules (Insecure)

Your current rules allow anyone to read and write to your database, which is a serious security risk:

// Your current rules - UNSECURE!
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read, write: if true;
    }
    match /tasks/{taskId} {
      allow read, write: if true;
    }
    match /assignedTasks/{taskId} {
      allow read, write: if true;
    }
    match /userTasks/{username} {
      allow read, write: if true;
    }
  }
}

These rules allow anyone on the internet to read, write, and delete all data in your database. This is extremely dangerous!

Updated Rules (Secure)

Here are secure rules for your attendance system that implement proper user-based authorization:

// Secure rules for attendance system
service cloud.firestore {
  match /databases/{database}/documents {

    // Users can read their own data, admins can read all user data
    match /users/{userId} {
      allow read: if request.auth != null &&
        (request.auth.uid == userId || exists(/databases/$(database)/documents/users/$(request.auth.uid)/admin));
      allow write: if request.auth != null && request.auth.uid == userId;
    }

    // Attendance records - users can read their own, admins can read all
    match /attendance/{recordId} {
      allow read: if request.auth != null &&
        (resource.data.userId == request.auth.uid || exists(/databases/$(database)/documents/users/$(request.auth.uid)/admin));
      allow create: if request.auth != null && request.auth.uid == request.data.userId;
      allow update, delete: if request.auth != null &&
        (resource.data.userId == request.auth.uid || exists(/databases/$(database)/documents/users/$(request.auth.uid)/admin));
    }

    // Leave requests - users can create and read their own, admins can manage all
    match /leaveRequests/{requestId} {
      allow read: if request.auth != null &&
        (resource.data.userId == request.auth.uid || exists(/databases/$(database)/documents/users/$(request.auth.uid)/admin));
      allow create: if request.auth != null && request.auth.uid == request.data.userId;
      allow update: if request.auth != null &&
        (resource.data.userId == request.auth.uid || exists(/databases/$(database)/documents/users/$(request.auth.uid)/admin));
      allow delete: if request.auth != null && exists(/databases/$(database)/documents/users/$(request.auth.uid)/admin);
    }

    // Admin-only collections
    match /admin/{document=**} {
      allow read, write: if request.auth != null &&
        exists(/databases/$(database)/documents/users/$(request.auth.uid)/admin);
    }
  }
}

These rules ensure that:

  • Users can only access their own data
  • Admins have special privileges to access all data
  • Only authenticated users can read/write data
  • Data validation is enforced

Before (Insecure)

  • Anyone can read your entire database
  • Anyone can modify or delete data
  • No user authentication required
  • No data validation
  • Extremely vulnerable to attacks

After (Secure)

  • Only authenticated users can access data
  • Users can only access their own data
  • Admins have special privileges
  • Data validation rules enforced
  • Protected against unauthorized access

Key Security Features

User-Based Authentication

Only authenticated users can access the database, and they can only access their own data.

Admin Privileges

Users with an 'admin' field in their document get special access to all data.

Data Validation

Rules ensure that data written to the database follows the expected format.

Prevent Unauthorized Access

Rules block unauthorized users from reading or modifying data they shouldn't access.

Implementation Steps

  1. Go to the Firebase Console and select your project
  2. Navigate to Firestore Database → Rules
  3. Replace the existing rules with the secure rules provided above
  4. Click "Publish" to deploy the new rules
  5. Update your user documents to include an 'admin' field for admin users

For admin users, make sure to add a boolean field called 'admin' set to true in their user document.

// Example user document for an admin
{
  "userId": "admin_uid_123",
  "name": "Admin User",
  "email": "admin@example.com",
  "role": "admin",
  "admin": true
}
